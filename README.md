# higgs_combine

The NIsoMuon counting workflow is in `NIsoMuon/limit_workflow.py`; review tasks
are in `NIsoMuon/combine_review.py`. The review Condor backend is in
`NIsoMuon/review_condor.py` and `NIsoMuon/review_bias_parallel.py`; keep both
beside `combine_review.py`. No separate
`qcd_stat_uncertainty.py` module or execution is required.

The DY consumer integrates the producer's signed `DYAux/LightJetSource` bins
before imposing the nonnegative counting-window yield. If the window integral
is nonpositive, the nominal DY yield is zero and its original source Sumw2
uncertainty enters the additive Gaussian `LightJetStat` with width
`NF_aMC * sigma(LightJetSource)`. NFStat and NFModel have no multiplicative
response in these channels; a zero-width source is a fixed zero process.
Positive-source windows retain the existing model. Signed central-yield and
source-error closure checks run before applying this boundary. This consumer
update requires rebuilt cards (`--stage all` or `--stage cards`); existing
signed DY/QCD ROOT inputs need no regeneration.

The data-driven QCD model includes additive statistical shifts in
addition to the existing Norm (`lnN`) and functional-form (`param`) uncertainties.
Each era's updated SKPlotMaker SS producer computes the statistical derivatives
in `qcd_bkg_estimation.py` and saves `QCDStat/metadata` (`NPS26009_QCDStat_v3`
for the default run-common transfer, v2 for legacy methods),
`CentralYield`, `FitGradient_0` through `FitGradient_4`, and the two `NFGradient_*`
histograms in `NIsoMuon_SS_fit.root`. The workflow sums these yield derivatives
over each actual counting window and propagates the stored full covariance;
it does not reconstruct or refit the SS function. For run-common transport,
low-data NF-stat + SS-fit-stat is an era-local conservative first-order bound
because their shared-SS cross-covariance is unknown. The common MC double-ratio
statistical component is independent of this bound and correlated within each
Run. Legacy v2 methods retain the full NF-stat + SS-fit-stat bound.
Covariance status 2 or 3 is accepted, including boundary solutions such as
`n = 0`. Where needed, Minuit2 regularises the covariance to be positive definite.
The workflow uses the saved matrix directly and reports its status and boundaries.

The rate is `max(0, shape-yield parameter + local statistical shift + common MC shift)` times Norm lnN,
with base QCD rate 1. Central fits and yields are retained. Statistical metadata
and central-template consistency are required even without `--strict`.
Blinded observations remain the unrounded nominal background-only expectation;
formula parameters are evaluated at their Gaussian means without reading SR data.

The legacy formula is `max(0.0,@0+@1)`; the common-transfer formula is
`max(0.0,@0+@1+sigmaMC*@2)`. A single standard Gaussian
`CMS_NPS26009_QCD_MCTransferStat_Run2` or `Run3` is shared by the relevant
channels; its yield coefficient comes from the producer-written derivative.
The local statistical width excludes that shared component, so it is not
counted twice. Mixed legacy/common templates or stale common-fit fingerprints
within a Run are rejected. The floating-point zero avoids an
ambiguous `TMath::Max` overload in ROOT. Rebuild cards containing `max(0,@0+@1)`
with `--stage cards` or `--stage all`; existing QCD ROOT files need no rerun.
Common-transfer changes require regenerated ROOT templates and rebuilt cards;
update SKPlotMaker and validate its Run2/Run3 double ratios first with
`qcd_bkg_estimation.py --mode ss-data --year Run2+3 --validate-qcd-double-ratio`.
This statistical compatibility test does not prove detector-effect cancellation.
Combine command failures stop immediately. Adaptive rMax expansion is based on
the collected limit output, rather than a non-zero command exit status.

Regenerate ROOT files for this storage format; metadata-only older files are
rejected. Run the per-era SS producer sequentially first (adaptive binning, target effective
count 10, maximum width 5 GeV), then in `NIsoMuon`:

```bash
python3 limit_workflow.py --stage cards --target runs --parameter alpha \
    --mode blind --sigfit-dir ./sigfit_inputs --strict
```

Inspect the `[QCD STAT]` lines and generated cards before using the usual
`--stage all` production command. Older contracts are rejected. Existing tracked
cards and fit/limit/review outputs have not been regenerated by this code update.
Detailed model documentation and historical review material are in
[combine_review](https://github.com/joonblee/combine_review). Use the current
`higgs_combine/NIsoMuon` scripts for the Condor review backend described below.

## Condor review and validation

From `NIsoMuon`, after activating the Combine CMSSW environment, submit the
representative-mass blind review against the current production counting cards:

```bash
REVIEW_BATCH="condor_jobs/review_$(date +%Y%m%d_%H%M%S)"
python3 -u combine_review.py --backend condor --review-suite \
  --target Run2Run3 --output-base review_outputs \
  --bias-toys 500 --hybrid-toys 500 \
  --condor-dir "$REVIEW_BATCH"
```

This submits a DAG and returns; it does not run the fits on the login host.
Workspace conversion and floating-parameter discovery happen once on the
submission host, so PyROOT/Combine are required when preparing the batch.
The suite includes card validation at M12/M20/M30/M70; r=1 Asimov
FitDiagnostics and S+B impacts at M12/M30/M70; r=0 fits/correlations and
signed-r likelihood scans at M20/M70; bias at 0/r95/2*r95 with interval
audits and flagged-toy repairs at M20/M70; and the blinded M70 HybridNew
cross-check. `r95` is read from the submitted internal-limit JSON; internal
r=1 does not mean alpha=1. Set `--bias-toys 500` explicitly to reproduce the
500-toy ensembles (the general helper default remains 200).

Each nuisance fit, scan chunk and HybridNew grid point is a separate
single-CPU Condor job. Bias generation is once per injection; fits use the
same saved toys with `--pickToy`, retaining their original toy IDs, in chunks
of 25 sequential fits per worker by default. Collectors merge the results and
use the existing local summaries, plots and nuisance-boundary repair logic.
The structural bias audit creates a lazy HTCondor Sub-DAG containing only
flagged toys: each toy repair gets a separate single-CPU worker, followed by
one strict merge. The refit and centre/lower/upper endpoint checks for one toy
retain their existing order and numerical criteria. No new toys are generated.
Already verified serial repairs can be reused only when their saved command
matches the same workspace, toy dataset/ID, injection and fitted range, and
all original numerical checks pass. All required toy results must pass before
the final summaries are published. Additional impact-boundary repairs still
run serially in their collector worker; they are not launched on the login host.
Use `--scan-chunk-size` (default 20) or `--bias-chunk-size` (default 25) to
change granularity. Local `--*-parallel` values do not control the Condor DAG;
worker-local process counts are fixed at one. `--condor-max-jobs N` optionally
caps active jobs per DAG, including each repair Sub-DAG independently; this is
not a global cap across nested DAGs. Zero, the default, leaves scheduling to the pool.
Each worker requests one CPU and 4000 MiB by default (`--condor-memory`).

The worker wrapper activates the submitted `CMSSW_BASE` and `SCRAM_ARCH` using
CVMFS and `scramv1 runtime -sh`. The CMSSW installation and all batch paths must
be accessible at the same absolute paths on every worker; files are not
transferred. `--condor-cmssw-base`, `--condor-scram-arch` and
`--condor-requirements` provide explicit site overrides. Only if the storage
really is shared but the advertised domains differ, use e.g.
`--condor-filesystem-domain tamsa2-ib0`. This changes matching metadata, not
filesystem access.

Cards, the expected-limit JSON, workspaces and helper code are snapshotted in
a new batch directory. Their SHA256 fingerprints are checked by workers and
collection; edits in the production checkout do not change submitted inputs.
`--condor-dry-run` prepares these snapshots and workspaces without submitting.
The backend currently accepts self-contained counting cards only.
Do not move or edit a submitted batch. Intermediate results stay under the
batch until successful collection; previous production review outputs are
not read as fit inputs.

After the DAG completes:

```bash
python3 combine_review.py --stage collect --condor-dir "$REVIEW_BATCH"
```

Collection refuses incomplete/stale results. It publishes the selected mass
directories under `review_outputs/<TARGET>/M<MASS>/`, retaining previous
versions under `<batch>/previous_outputs/`, and writes `review_collection.json`.
FitDiagnostics summaries are JSON; fitted status/covariance, scans, bias and
HybridNew outputs still require statistical review. Job completion alone is
not evidence that those checks pass.

Likelihood-scan collectors now write `scan_validation_M<MASS>.json` before
plotting. The audit checks the original bin-centred grid coordinates, finite
NLL values, consistent initial minima across chunks, and complete grid support
through the plotted region below `2*deltaNLL=7`. Both sides of the level-1 and
level-4 crossings must be bracketed. Missing, invalid or above-cut interior
points are retried individually at their original coordinates with tighter
minimiser settings; no new grid, dataset or statistical model is substituted.
At least two successful retries must agree within 0.005 in deltaNLL. Their
initial global fits must have status 0, covariance quality at least 2 and
EDM at most 0.001; their NLL reference must agree with the original within
0.001. These saved fit statuses refer to the initial fits: the original grid
does not provide a saved per-point RooFitResult/EDM audit. The raw grid ROOT
file remains unchanged, and plots use a separate `scan_validated_M<MASS>.root`
with the legend `Background-only Asimov`. Failed or missing tail points outside
the bracketed plotted region are reported separately rather than declared
converged. Unresolved interior holes or unbracketed crossings prevent collection.

For the published pre-audit review batch, after its queue is empty, use the
same `--stage resume` command below. It prints `[SCAN AUDIT]`, backs up the
known helper snapshots and updates only the M20/M70 scan collectors. Completed
scan chunks, bias repairs, impacts and other jobs are retained. The collectors
inspect the server-local ROOT rows and record whether each gap was a missing
entry, an invalid value or a point removed by the plotting cut. Unknown helper
snapshots are rejected. Run `--stage collect` once the scan collectors finish;
an old successful collector without the new audit is no longer sufficient.

If a node failed, first ensure this batch's DAG manager and workers have left
the queue (including held jobs), then run:

```bash
python3 combine_review.py --stage resume --condor-dir "$REVIEW_BATCH"
# After recovery completes:
python3 combine_review.py --stage collect --condor-dir "$REVIEW_BATCH"
```

Batches created by the first Condor review backend (commit `85a89eb`) had an
output-name bug for bias fits: Combine appends `.123456` to MultiDimFit output
names when `-t` is positive, but the backend expected no seed suffix. After
updating the checkout and waiting for that batch's jobs/DAG manager to leave
the queue, migrate and resume that known version with:

```bash
python3 combine_review.py --stage resume --upgrade-backend \
  --condor-dir "$REVIEW_BATCH"
```

This archives the original manifest/code and affected status records, updates
only the known filename contract and backend snapshot, and keeps the original
fit commands, seeds, cards and toys. A bias chunk is recovered without rerunning
its fits only when all commands exited zero and its sole recorded failure was
the missing expected filename; all corrected output files and command logs must
exist, and the saved-toy dependency must still match. Interval audit/repair is
still required downstream. Other failures are retried as usual. This migration
accepts only the original published backend/helper fingerprints; arbitrary
snapshot edits are rejected. Collection now prints the worker's recorded error
and log directory instead of only a generic failed-status message.

Resume uses the frozen code/input snapshot, retains valid completed jobs and
resubmits failed, pending or stale nodes and their affected descendants. It
refuses to submit a second DAG while jobs in the same batch remain queued.
Completion UUIDs prevent descendants from being accepted after a dependency
was rerun. Worker logs/status are in `<batch>/jobs/job_<index>/`.

To convert incomplete serial bias-audit nodes from the `910d62a` backend
in an existing batch, first wait for its DAG and workers to finish or remove
that specific DAGMan job with `condor_rm`. The command below refuses to change
a batch while it or any child workflow still has queued/running/held jobs.

```bash
python3 combine_review.py --stage resume --parallel-bias-repair \
  --condor-dir "$REVIEW_BATCH"
```

The conversion archives the original snapshot/manifest, retains completed
production fits and completed audits, and replaces only incomplete audits.
Verified per-toy results already saved by a serial repair are considered for
reuse; unverified attempts are retained but never accepted as passed results.
The structural audit submits only remaining flagged repairs, rather than jobs
for all toys. Subsequent recovery uses ordinary `--stage resume`; valid child
jobs are retained and only failed/stale repairs and their merge are retried.
The child manifests/logs are under `<batch>/bias_repairs/<TARGET>/M<MASS>/`;
merged bias summaries are under the mass result's
`bias_checks/parallel_verified/`. A running frozen batch does not automatically
adopt code changes made in the production checkout.

Sub-DAG descriptions are generated after their structural audit and submitted
lazily by DAGMan on the access point, using `SUBDAG EXTERNAL` with an explicit
child working directory. See the
[HTCondor Sub-DAG documentation](https://htcondor.readthedocs.io/en/24.x/automated-workflows/dagman-using-other-dags.html).
Workers do not submit jobs themselves. `--stage collect` validates child job
completion, output fingerprints and dependency completions recursively.

For batches frozen at `8e52715`, update the checkout and run ordinary resume
after the batch and its child jobs have left the queue:

```bash
git pull --ff-only
python3 combine_review.py --stage resume --condor-dir "$REVIEW_BATCH"
```

Resume recognises the exact published helper fingerprints, archives the old
snapshot and manifest under `review_patch_*`, and prints `[REVIEW PATCH]`.
Completed fits, cards, workspaces, saved toys and job configurations are retained.
New Sub-DAG directories are created before outer-DAG parsing; audit preparation
accepts an empty directory, while refusing to overwrite existing repair files.
There is no need to delete or recreate the M20 directory manually.

Ordinary resume also updates the published per-toy repair helper in incomplete
repair Sub-DAGs, printing `[BIAS REFINE]` and archiving every replaced helper,
manifest and audit-parent status under `bias_refinement_upgrade_*`. Accepted
toy repairs keep their completion records and are not rerun. After the original
three retries, failed toys receive tighter Strategy 1/2 fits. A finite saved
candidate with valid status/covariance can initialise those fits, including
all its nuisance values; a high-EDM candidate is never itself accepted. The
seeded fits omit the preliminary POI-only search and the coarse fallback.
They use the same saved toy, ID and POI range, with all nuisances floating.
The final status, covariance, EDM <= 0.001, centre and endpoint checks remain
mandatory. Live Combine convergence must still be verified in the original
CMSSW runtime.

Collapsed QCD-stat Gaussian impact intervals with tiny absolute prior widths
are checked using conditional profiles at the centre and both prior-sigma
points. A small width never implies zero impact: the measured POI values and
deltaNLL (zero at the centre and 0.5 at each endpoint, within numerical
tolerances) must pass validation before publication. Failed checks remain
errors. Reports and per-strategy logs are retained under
`impact_repair_M<MASS>/tiny_gaussian_profiles/`.

Individual tasks also support Condor, for example:

```bash
python3 combine_review.py 70 --backend condor --task hybrid \
  --hybrid-toys 500 --condor-dir condor_jobs/review_hybrid_M70
```

Local commands remain available with `--backend local` (the default), including
`--task fitdiag --inject-r 1`. Run the ROOT-free scheduler contracts with
`python3 -m unittest discover -s NIsoMuon/tests -p test_review_condor.py -v`

For `limit_workflow.py`, Condor is the default execution backend, with no workflow concurrency cap.
Use `--local` to run directly on CPU cores. For local limits, `--jobs` caps

Combine output is saved separately to
`limit_outputs/alpha/<mode>/<target>/combine_*_attempt*.log`;

## Individual eras and partial unblinding

Individual-era cards, fits and limit plots use the same statistical model as
the run combinations. Choose the scope explicitly:

| Selection | Options |
| --- | --- |
| One era | `--target 2018` |
| Selected eras, fitted separately | `--target eras --eras 2018,2022` |
| All eight individual eras | `--target eras` |
| Run-2, Run-3 and Run-2+3 combinations | `--target runs` |
| All run combinations and individual eras | `--target all` |

The supported eras are `2016preVFP`, `2016postVFP`, `2017`, `2018`, `2022`,
`2022EE`, `2023` and `2023BPix`. `--eras` is valid only with `--target eras`;
it does not redefine what Run2 or Run3 means. `--masses 12,30` additionally
selects mass hypotheses. The luminosity and energy labels follow each era.

For partial unblinding, use `--mode unblind` with the chosen individual era(s).
Only those eras' SR observations are read when building cards. For example,
to build and run observed limits for 2018 locally:

```bash
python3 -u limit_workflow.py \
  --stage all --task limits --target 2018 --mode unblind \
  --parameter alpha --sigfit-dir ./sigfit_inputs --local --jobs 40 --r-max 100 --strict
```

For each unblind card, the observed limit comes from data and the expected
bands from a separate `--run blind` fit. The default remains `--mode blind`.
Cards are under `datacards_NIsoMuon/alpha/<mode>/per_year/<era>/`; plots and
physical-limit JSON are under `limit_outputs/alpha/<mode>/<era>/`, named
`limits_<era>_alpha.*`. Use `--stage all` to build the selected era cards first;
`--stage run` requires existing cards for the requested mode and targets.

## HTCondor execution (default)

No backend option is needed. `limits`, `impacts`, `fitdiag`, `checks` and
`all` support Condor with `--stage run` or `all`. `--stage cards` only builds
cards and submits nothing. `--stage all` builds cards before submitting;
`--stage run` snapshots existing cards. `--backend local/condor` remains
available for compatibility; `--local` is the explicit CPU-execution option.

| Task | Condor jobs |
| --- | --- |
| `limits` | One job per target/mass; observed and blind-expected fits run sequentially inside it |
| `impacts` | Initial-fit job, one job per nuisance, then a collection/validation/plot job for each target/mass |
| `fitdiag`, `checks` | One FitDiagnostics/pulls job per target/mass |
| `all` | Limit and FitDiagnostics jobs plus the full impact DAG |

For fresh impacts, workspaces are built and their floating parameter lists
read on the submission host. A DAG connects the subsequent fits: nuisance
jobs start after the initial POI interval passes validation and any lower-range
expansion; the final job waits for every nuisance fit. All nuisance fits use
the same saved workspace, initial fit and range. The final Condor job runs
the existing interval checks, failed-scan retries, physical QCD-boundary
profiles, alpha conversion and impact plotting. These final repairs run
serially within that job's allocated CPU. The statistical model and fit
prescription are shared with local execution.

The `submit.jds`, process-index worker argument, `job_<N>.log/.err`,
`condor.log`, vanilla universe and optional `n<N>.<USER>` concurrency limit
follow `SKFlatAnalyzer/python/SKFlat.py`. Workers initialise CMS via CVMFS
and `scramv1 runtime -sh` in the active **Combine** `CMSSW_BASE`, using the
active `SCRAM_ARCH`. Both can be overridden with `--condor-cmssw-base` and
`--condor-scram-arch`.

This backend requires the CMSSW area and batch/output directories to be on
storage shared with worker nodes. It uses `should_transfer_files = NO` and
does not package a CMSSW installation. Each job requests one CPU and 4000 MiB
by default, and sets OpenMP/BLAS thread counts to one. `--condor-memory`
changes memory; `--condor-requirements` supplies site-specific requirements.

From `NIsoMuon`, after initialising the Combine environment, the Condor
equivalent of the 2018 partial-unblinding example is:

```bash
python3 -u limit_workflow.py \
  --stage all --task limits --target 2018 --mode unblind \
  --parameter alpha --sigfit-dir ./sigfit_inputs --r-max 100 --strict \
  --condor-dir condor_jobs/2018_unblind
```

To distribute blind impacts for Run-2, Run-3 and Run-2+3:

```bash
python3 -u limit_workflow.py \
  --stage run --task impacts --target runs --mode blind \
  --parameter alpha --masses 12,30,70 \
  --allow-negative-r --r-min -50 --r-max 100 --strict \
  --condor-dir condor_jobs/impacts_blind
```

Use `--task all` to submit limits, diagnostics and impacts together.
`--impact-masses` still selects which masses receive impact jobs.
`--repair-impacts` also supports Condor: it snapshots the existing workspace,
scans, internal JSON and repair caches, then runs the repair for each selected
target/mass as a Condor job. Existing original results are updated only when
that batch is collected successfully.

`--condor-nmax` defaults to **0**, so no `concurrency_limits` entry or
workflow job cap is emitted. Normal pool and DAGMan policies still apply.
Optionally add `--condor-nmax 40` (alias `--condor_nmax 40`) for the same
site-configured `n40.<USER>` convention as SKFlatAnalyzer.
`--condor-batch-name` sets the batch name. Aliases `--nmax`, `--memory`,
`--batchname` and `--no-exec` match the SKFlat naming. `--jobs` and
`--impact-parallel` are local-only; select `--local` to use them.

Examples of local CPU execution:

```bash
python3 limit_workflow.py --local --stage run --task limits --target runs --jobs 40
python3 limit_workflow.py --local --stage run --task impacts --target runs --impact-parallel 40
```

Add `--condor-dry-run` to prepare the submission without enqueuing jobs, then
submit manually from the generated directory with the printed command:
`condor_submit submit.jds` for flat jobs or `condor_submit_dag workflow.dag`
for impacts/`all`. Dry-run still prepares workspaces for fresh impacts and
builds cards if `--stage all` was requested. Choose a new
`--condor-dir` for each submission; existing directories are not overwritten.
Omitting it creates a unique directory under
`<output-base>/condor/<parameter>/<mode>/`.

After completion, collect using the printed command, or for this example:

```bash
python3 condor_jobs/2018_unblind/limit_workflow.py \
  --stage collect --condor-dir condor_jobs/2018_unblind
```

Collection restores the saved mode, targets, masses and options from the
manifest; no other CLI options are accepted at this stage. It runs no fits.
Limit collection and plotting run at this stage; impact plots have already
been validated in the final DAG job and are published here.
Each batch retains its workflow snapshot, datacards, `manifest.json`, and
separate `jobs/job_<N>/` fit outputs and completion status. Later edits to
the original cards do not change a queued fit or its alpha conversion.
Pending/failed jobs, changed snapshots, missing outputs and downstream
results from a superseded dependency stop collection before publication.
Final plots/JSON use the usual output directory. Impact workspaces/scans and
repair reports are also published there for subsequent `--repair-impacts`;
the batch retains its isolated originals and logs. Limit ROOT files remain
in the batch directory. Set
`--output-base` at submission to retain a separate production's final plots.

The orchestration tests use synthetic Combine executables to exercise batch
preparation, concurrent workers, DAG dependencies, initial-range expansion,
collection, era selection, blinding, repair and alpha conversion without ROOT.
They do not validate a live pool or physical limits.

## Optional resolution-based mass scan

`NIsoMuon/limit_workflow.py` still defaults to the available simulated masses.
Add `--interpolate-signal` to build and fit each intermediate hypothesis. The
limits themselves are never interpolated. Run from the production directory
with the existing ROOT inputs, `sigfit_inputs/` and Combine environment:

```bash
# Run from NIsoMuon; keep mass_scan_grid.json beside the script.
workflow=./limit_workflow.py

python3 "$workflow" --stage all --task limits --target runs \
  --parameter alpha --mode blind --interpolate-signal \
  --sigfit-dir ./sigfit_inputs --backend condor --r-max 100 \
  --condor-dir condor_jobs/interpolated_blind \
  --plot-limits-py "$PWD/python/plotLimits.py" --strict

# After every Condor job has finished, collect and plot the results.
python3 condor_jobs/interpolated_blind/limit_workflow.py \
  --stage collect --condor-dir condor_jobs/interpolated_blind
```

For one era, replace `--target runs` with e.g. `--target 2016preVFP`.
`--mode` retains its existing behaviour; the scan option does not unblind data.
Execution defaults to Condor, matching the current production workflow.
`--stage all` builds cards and submits jobs; it does not wait for their completion.
Use the printed collect command after the jobs finish. A single-era full scan
submits 229 mass jobs; each unblind mass job performs the observed fit and a
separate blind-expected fit. There is no default workflow concurrency cap;
`--condor-nmax 40` optionally applies the existing site concurrency limit.
For local execution instead, use `--local --jobs 40`. `--jobs` is local-only.
Omit `--masses` to use the complete shared grid. With interpolation enabled,
`--masses 12,12.5,15,20` instead selects exactly those hypotheses (including
off-grid points inside the supported interval). Without interpolation, the
existing simulated-mass selection is unchanged.

The frozen `NIsoMuon/mass_scan_grid.json` contains **229 hypotheses from 12 to
70 GeV**, including all 13 original sample masses. It is common to every era,
Run 2, Run 3 and Run 2+3. The reference curve is the equal-era arithmetic mean
of the eight stored fits to `sigma_m/m = a*m+b`, with
`a=0.0001331148680501898 /GeV`, `b=0.012312862256709963`. This is a sampling
reference, not a fit to the combined signal distribution. Successive scan
steps are at most half this reference sigma, rounded down to 0.001 GeV; the
additional original sample masses can shorten a step. Before those insertions,
the spacing grows from about 0.083 GeV to 0.75 GeV. The JSON pins the source
fit commit and all eight coefficient pairs. The grid is not regenerated from
the requested era or from new local fits. To deliberately replace it, provide
`--mass-grid-file FILE` with `{"schema_version":1,"masses":[12,12.5,15,20,70]}`.
These values are **mass hypotheses, not histogram bin edges**. Per-era fitted
resolution, `--n-sigma`, source histogram bin integration and window truncation
remain unchanged.

At an existing sample mass, signal inputs are read directly as before. Between
samples, the selected signal yield and each requested Up/Down yield are
interpolated log-linearly in mass, separately for each era. Each anchor is
integrated in its own original counting window. This is the counting-yield
prescription implemented in `SKPlotMaker/sigFit_v2.py`; it does not require
regenerating `signal_interpolation.json`. Applying the same log interpolation
to nominal and varied yields also interpolates their multiplicative ratios
log-linearly. Independent anchor Sumw2 errors are propagated through the
interpolation and used for the existing signal MC-stat nuisance. They are not
an interpolation-model uncertainty. Luminosity and nuisance correlations are
unchanged. Optional signal generator variations are included if requested.
In xsec mode, a supplied mass-dependent reference cross-section map is also
log-interpolated; alpha mode retains its per-card internal scaling.

Background yields, QCD fit derivatives/covariance and transfer statistics, DY
light-jet statistics/NF terms, and other background variations are read at
**each new window**. They are not interpolated from the old cards. No new
background fit is required solely to add scan points, provided the current
producer ROOT files contain their full templates and QCDStat/DYAux inputs.
The original nominal and systematic signal ROOT files at bracketing masses
are also required. Missing/non-positive signal inputs and extrapolation fail
before existing cards are removed. The supplied grid starts at 12 GeV; it
does not infer an 11 GeV signal from samples starting at 12 GeV.

Default outputs are `datacards_NIsoMuon_interpolated/` and
`limit_outputs_interpolated/`. Explicit non-default `--card-base` and
`--output-base` are honoured. To separate generation from fitting, first use
`--stage cards`; later use `--stage run --interpolate-signal` with the same
grid/masses and card base. The run stage requires no histogram/sigfit inputs
but checks that all requested cards exist and match the grid fingerprint.
The grid JSON must remain alongside the standalone script if it is copied.
Condor submissions snapshot the grid beside the worker script and save its
fingerprint in the manifest. Workers, collection and resume use that snapshot,
so later checkout/custom-grid changes do not change submitted hypotheses.

`signal_interpolation_audit.json` beside `card_summary.json` records the grid,
resolution inputs, anchor yields/errors/windows, per-point anchor choices and
leave-one-out residuals for yields and systematic ratios. Review these
residuals before adopting the interpolated scan as a final analysis result;
no new interpolation nuisance is added automatically. The same checks can be
reproduced with the upstream signal fitter. A small `--masses` subset can
have too few native anchors for a leave-one-out check; use the full scan to
obtain closure over the full mass range.

## Recovering an incomplete Condor batch

After updating the repository, run recovery with the **current** driver:

```bash
python3 limit_workflow.py --stage resume \
  --condor-dir condor_jobs/2016preVFP_unblind
```

This submits only failed, pending or stale nodes and their affected downstream
nodes. Successful limits, diagnostics, initial fits and nuisance scans are
retained. If only `impact_final` nodes failed, only those final nodes are
resubmitted. Recovery creates a new code snapshot, DAG and logs under
`<batch>/resume_<timestamp>_<id>/`; the original workflow snapshot, manifest,
cards and fit inputs are preserved. Worker completion records include the
code path and SHA256. `--condor-dry-run` prepares recovery without submitting;
`--condor-nmax` and `--condor-memory` optionally override its saved resources.

When recovery finishes, publish using the current driver and original batch:

```bash
python3 limit_workflow.py --stage collect \
  --condor-dir condor_jobs/2016preVFP_unblind
```

The original batch snapshot intentionally keeps the original code. Run
`--stage resume` from the updated top-level `limit_workflow.py` to use a fix.
Collection now reports each failed node's kind and recorded error directly.

ROOT-free statistical/card contract tests: `python3 -m unittest discover -s NIsoMuon/tests -v`.

## Repairing incomplete blind impacts

After a completed impact run, use `--repair-impacts` with `--stage run --task impacts` and the same `--output-base`. This preserves existing workspaces and original ROOT scans. Only missing scans and collapsed nuisance intervals are retried with strategy 2. A zero shift of the POI is permitted when the nuisance interval itself is valid.

For a QCD shape lower interval truncated by its physical zero bound, the workflow runs a conditional MultiDimFit with the shape parameter fixed at zero and r floating. It records the conditional r and deltaNLL in `boundary_endpoints`; a boundary profile is accepted only if two fit entries exist, r lies inside its range, and deltaNLL is below 0.51 (0.5 plus numerical tolerance). The statistical model and datacards are unchanged.

Observed boundary profiles start at the validated initial POI best fit;
blind profiles preserve their original signal injection. Missing conditional
entries, failed commands or invalid endpoint results trigger strategies 2, 1
and 0 with Minuit2/Migrad fallbacks, without changing fit ranges or likelihood
acceptance criteria. Each attempt's log and ROOT file, plus any previous
boundary output, is archived in a unique `attempts_*` subdirectory.
`fit.log` is the latest attempt and `profile_validation.json` records a
successful endpoint. A one-entry output is never accepted just because the
Combine command exits zero.

The full nuisance list is checked against the workspace. Missing scans or invalid intervals cause a non-zero exit, even when Combine collection returns zero. The original internal JSON is retained as `*.before_repair.json`. Retry logs, boundary fit ROOT files and `validation.json` are stored under each target's `impact_repair_M<mass>/` directory. JSON and impact plots are updated only after successful validation. A subsequent standalone combineTool collection from the original ROOT files does not include these repaired endpoints; use the workflow's repaired internal JSON.

Example from the NIsoMuon directory after cmsenv:

```bash
python3 -u limit_workflow.py \
  --stage run --task impacts --repair-impacts \
  --target runs --parameter alpha --mode blind \
  --masses 30,70 --impact-masses 30,70 \
  --local --impact-parallel 40 --sigfit-dir ./sigfit_inputs \
  --qcd-method data-driven --dy-method data-driven \
  --allow-negative-r --r-min -5 --r-max 10 \
  --output-base limit_outputs_impacts_retry --strict \
  > impacts_blind_repair.log 2>&1
```

For these six selected results, success is six `[IMPACT CHECK]` lines followed by the final `[DONE]`. Failure prints an `[ERROR]` with the location of the corresponding log. This repair does not rerun AsymptoticLimits or rebuild background estimates.
